# 知识库采集与审计规范

本项目是支持层项目，用于为其他交易、回测、模拟盘、实盘风控、LLM 训练和 RAG 项目提供专业知识库。任何知识进入本项目前，都必须经过资料检索、来源评估、结构化归类、冲突检查和审计记录。

## 核心原则

```text
项目事实留在业务项目。
通用专业知识进入本支持层。
任何专业细节都必须有来源。
任何理论冲突都必须被显式标注或消解。
任何时效性规则都必须标注更新时间和失效风险。
```

## 知识采集流程

1. 明确知识问题

```text
示例：
1m K线回测中，同一根 K 线同时触发 TP 和 SL 时，应该如何判定先后？
```

2. 联网检索资料

优先级从高到低：

```text
P0: 官方文档、交易所规则、标准协议、原始论文、权威数据源
P1: 开源项目官方文档、工程白皮书、主流框架文档
P2: 专业书籍、课程、研究报告、行业文章
P3: 博客、论坛、经验贴，仅可作为补充，不能单独作为核心规则依据
```

3. 记录来源

每条知识至少记录：

```json
{
  "source_title": "",
  "source_url": "",
  "source_type": "official_doc | paper | exchange_rule | framework_doc | book | research_report | engineering_article",
  "publisher": "",
  "published_at": "",
  "accessed_at": "",
  "version": "",
  "reliability": "high | medium | low"
}
```

4. 提炼知识规则

每条规则必须写清楚：

```text
规则本身
适用场景
不适用场景
前置假设
数据粒度
市场类型
时间周期
可能副作用
验证方式
```

5. 冲突检查

新增知识必须和同 domain、subdomain 下已有知识做冲突检查。

冲突类型：

```text
direct_conflict: 两条规则结论相反
scope_conflict: 规则成立条件不同，但文本未声明
version_conflict: 新旧版本规则差异
market_conflict: 现货、合约、股票、期货、加密市场适用性不同
granularity_conflict: tick、秒级、1m K线、日线适用性不同
assumption_conflict: 成本、滑点、流动性、撮合假设不同
```

6. 冲突消解

禁止简单删除一方。必须按下面顺序处理：

```text
1. 判断来源等级
2. 判断适用市场
3. 判断数据粒度
4. 判断时间版本
5. 判断前置假设
6. 判断是否需要保留为多分支规则
7. 标注推荐默认规则
```

## 审计输出要求

每次新增或修改知识，Codex 必须输出：

```text
1. 本次新增/修改了哪些知识
2. 每条知识的来源
3. 是否发现冲突
4. 冲突如何消解
5. 哪些规则适合进入 RAG
6. 哪些规则适合进入 Skill
7. 哪些内容仍需人工确认
```

## 禁止事项

```text
1. 禁止无来源知识入库。
2. 禁止把项目私有字段写入通用知识。
3. 禁止把时间敏感规则当成永久规则。
4. 禁止把不同市场、不同粒度的规则混成一个结论。
5. 禁止只保存结论，不保存证据和适用条件。
6. 禁止让互相矛盾的规则同时处于 approved 状态，除非已经标注适用边界。
```
