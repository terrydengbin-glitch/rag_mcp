# 2. 核心原则

这套系统必须遵守 6 个原则。

## 原则 1：通用知识中心化

不要把知识复制到每个项目。

```text
错误方式：
project_a/docs/一堆微结构知识
project_b/docs/一堆微结构知识
project_c/docs/一堆微结构知识

正确方式：
central_knowledge_base/
  quant_trading
  kline_strategy
  backtest
  simulation
  live_trading
  llm_training
```

项目只引用知识库，不重复维护知识库。

---

## 原则 2：项目事实本地化

通用知识库不能写死项目字段。

例如：

```text
move_side
preferred_side
micro_fast
reason_code
trade_quality
```

这些可能只属于某个项目。
所以项目事实必须留在项目 repo 里。

```text
通用知识库负责：
OFI 是什么、CVD 怎么用、Funding/OI 如何解释、回测偏差有哪些

项目 repo 负责：
当前字段叫什么、当前 pipeline 怎么跑、当前配置是多少、当前代码路径在哪里
```

---

## 原则 3：能力 Skill 化

不要靠长 prompt 教 Codex。
重复出现的专业工作流，都做成 Skill。

Codex 官方建议把可重复工作变成 Skills，而不是每次靠长提示词重复说明；Skills 在 CLI、IDE extension 和 Codex app 中可用。([OpenAI 开发者][2])

---

## 原则 4：知识检索 MCP 化

Codex 不应该直接依赖某个项目里的 markdown。

长期应该通过 MCP 统一检索：

```text
search_expert_knowledge()
get_domain_playbook()
get_reason_code()
get_project_adapter()
```

Codex MCP 配置可以放在 `~/.codex/config.toml`，CLI 和 IDE extension 共用该配置；也可以按项目放在 `.codex/config.toml`。([OpenAI 开发者][3])

---

## 原则 5：交易研发全链路统一接口

你的回测、回放、模拟盘、实盘，不应该是四套策略逻辑。

应该统一成：

```text
同一个 Strategy Interface
同一个 Feature Snapshot
同一个 Decision Result
同一个 Risk Gate
同一个 Order Intent
不同的是 Data Source 和 Execution Adapter
```

这样 Codex 审计任何阶段时，才能用同一套专业标准判断问题。

---

## 原则 6：LLM 训练和 RAG 分工明确

这条非常重要：

```text
RAG 解决：模型不知道什么
SFT 解决：模型不会按流程做
DPO / Preference 解决：模型输出不符合偏好
Eval 解决：模型到底有没有变好
```

不要把最新市场事实、Binance 最新规则、项目当前配置训进模型。
这些应该进入 RAG。
而审计格式、交易分析流程、任务卡写法、老马看盘风格，可以进入 SFT / DPO。

Hugging Face TRL 官方文档说明 TRL 支持 SFT、GRPO、DPO、Reward Modeling 等 post-training 方法，因此 LLM 训练能力包应该把 SFT、偏好训练、评测拆成独立工作流。([Hugging Face][4])

# 4. 分层设计

## Level 0：Global Codex Rules

路径：

```text
~/.codex/AGENTS.md
```

作用：

```text
定义所有项目通用的工作方式
```

建议内容：

```md
# Global AGENTS.md

你是交易量化与 AI 工程助手。

## 通用原则
1. 所有策略建议必须拆分为：方向、进场、止损、止盈、仓位、执行、风控、数据质量。
2. 任何交易系统改动必须说明：
   - 输入字段
   - 输出字段
   - 影响模块
   - 是否影响交易频率
   - 是否影响胜率 / RR / EV
   - 如何验证
   - 如何回滚
3. 不允许用“感觉”替代数据验证。
4. 不允许只看收益率，必须同时看胜率、平均 R、回撤、持仓时间、坏桶、成本。
5. 遇到 LLM 训练需求，先判断是 RAG、SFT、DPO 还是 Eval 问题。
6. 项目事实永远优先于通用知识。
```

## Level 3：RAG / Knowledge Store

第一阶段建议：

```text

```

第二阶段升级：

```text
RAGFlow + Qdrant + LlamaIndex
```

理由：

* RAGFlow 适合做复杂文档知识库和 Agent context layer。它官方仓库将其定位为开源 RAG 引擎，并融合 RAG 与 Agent 能力。([GitHub][6])

## 5.4 Replay Engine Domain

行情回放不是普通回测，它的目标是：

```text
重建当时系统看到的市场状态
检查策略是否在当时应该出手
检查错过、误判、慢反应、提前进场
```

Replay 必须支持：

```text
1. 按时间推进
2. 按事件重放
3. 按 symbol 重放
4. 按 bad trade case 重放
5. 按策略版本重放
6. 支持 pause / step / fast-forward
7. 支持重算 feature snapshot
8. 支持对比不同版本策略输出
```

核心输出：

```json
{
  "case_id": "BTCUSDT_2026_06_08_001",
  "replay_window": ["2026-06-08T10:00:00Z", "2026-06-08T11:00:00Z"],
  "market_context": {},
  "strategy_v1_decision": {},
  "strategy_v2_decision": {},
  "difference": {},
  "diagnosis": "v1 entered before 3m confirmation; v2 waited for pullback",
  "recommendation": []
}
```

## 5.5 Simulation / Paper Trading Domain

```text
低保真模拟盘：

高保真模拟盘：
```

你当前更适合的高保真路线：

```text
第一阶段：1m K线模拟
第二阶段：秒级 K线模拟
第三阶段：aggTrade + bookTicker 模拟
```

```text
是否有 lookahead bias

是否考虑手续费
是否考虑滑点
是否考虑最小下单量
是否考虑 maker/taker
是否考虑 Binance min notional
是否考虑订单部分成交
是否考虑撤单失败
```

## LLM 训练决策树

```text
问题：模型不知道专业知识？
  → 用 RAG

问题：模型知道，但不会按你的格式输出？
  → SFT

问题：模型两个答案都能写，但不符合你的偏好？
  → DPO / ORPO / KTO

问题：模型回答质量不稳定？
  → Eval + bad case regression

问题：模型推理慢 / 贵？
  → 量化 / vLLM / SGLang / 小模型蒸馏

问题：模型幻觉？
  → 先检查数据、RAG、引用、评测，不要盲目继续训练
```

## LLM 数据类型

你的交易系统可以产生 5 类训练数据：

```text
1. 审计型数据
输入：代码 / 策略文档
输出：问题、风险、改进方案、验证指标

2. 交易分析型数据
输入：交易记录 + 行情上下文
输出：bad case 归因、优化建议

3. 策略设计型数据
输入：交易目标
输出：策略结构、字段、模块、测试计划

4. 发帖/表达型数据
输入：行情状态
输出：老马看盘风格内容

5. 偏好排序型数据
输入：同一个问题的多个回答
输出：chosen / rejected
```

## 检索策略

不要只做向量搜索。
建议：

```text
Hybrid Search = Dense Embedding + BM25/Sparse + Metadata Filter + Rerank
```

Qdrant 的 hybrid query 支持 dense、sparse、multivector 等多路结果，并可用 RRF 或 DBSF 融合；没有 eval set 时，RRF 是较安全默认选择，有 eval set 时可以调权重。([Qdrant][7])

检索流程：

```text
query
  ↓
domain router
  ↓
metadata filter
  ↓
dense search + sparse search
  ↓
RRF fusion
  ↓
rerank
  ↓
source quality filter
  ↓
return top_k with citation
```

# 14. 验证标准

任何 Codex 生成的策略修改，都必须通过下面这些验证。

## 策略验证

```text
1. 是否提升平均 R
2. 是否提升 Profit Factor
3. 是否降低最大回撤
4. 是否降低连续亏损
5. 是否改善时间坏桶
6. 是否降低噪音止损
7. 是否提高 TP 触达率
8. 是否没有过度减少交易机会
```

---

## 回测验证

```text
1. 无未来函数
2. 成本模型明确
3. 撮合规则明确
4. TP/SL 同 K 线处理明确
5. train/test 时间切分明确
6. 不只看全局收益，要看分桶表现
7. 策略版本可复现
```

---

## 模拟盘验证

```text
1. 模拟成交和真实成交差距
2. 信号生成和下单延迟
3. 订单状态是否完整
4. SL/TP 是否真实挂出
5. 撤单/改单是否被记录
6. 交易结果是否自动进入 trade analysis
```

---

## 实盘验证

```text
1. API 权限最小化
2. 单笔风险限制
3. 日内亏损限制
4. 连亏停机
5. kill switch
6. 仓位对账
7. 订单状态机
8. 事故恢复流程
```

---

## LLM 验证

```text
1. 是否减少幻觉
2. 是否提升格式遵循
3. 是否提升专业归因质量
4. 是否能稳定引用知识库
5. 是否在 bad case regression 上变好
6. 是否没有遗忘基础能力
7. 是否成本和延迟可接受
```

# 17. 最终建议

你应该做的不是：

```text
一个量化知识库
```

而是：

```text
一个可复用的 Trading + AI Codex 专家能力系统
```

核心组合是：

```text
AGENTS.md
负责全局行为约束

Skills
负责专业工作流复用

RAGFlow / Qdrant
负责专业知识检索

MCP
负责让 Codex 跨项目调用知识

Project Adapter
负责每个项目的轻量接入

统一交易接口
负责回测、回放、模拟盘、实盘一致性

Trade Analysis
负责把交易结果变成优化样本

LLM Training Domain
负责把你的交易分析能力训练成稳定模型能力
```

一句话总结：

**这套方案的目标，是让 Codex 在任何交易项目里，都能像一个懂量化、懂 K 线、懂回测、懂模拟盘、懂实盘风控、懂 LLM 训练的工程合伙人一样工作；项目只提供事实，能力由专家包复用。**
